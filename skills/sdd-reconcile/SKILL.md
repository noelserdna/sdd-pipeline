# Skill: sdd-reconcile — Spec-Code Drift Detection & Alignment

> **Version:** 1.1.0
> **Pipeline position:** Lateral — requires both SDD artifacts and code
> **Reads from:** `requirements/`, `spec/`, code and test paths from the SDD Stack Profile (`code_paths`/`test_paths`; defaults `src/`, `tests/`), `.sdd/gap-analysis.json` (optional)
> **Recommended by:** `sdd-pipeline-status --diagnose` (SDD drift, Partial SDD, Brownfield with docs)

## 1. Scope

Compares `requirements/` and `spec/` against the current code, classifies each divergence, amends the specs for the cases that are safe or that the user decides, and writes `reconciliation/RECONCILIATION-REPORT.md`.

It does not modify code or tests (they are the evidence of current behaviour), does not create SDD artifacts from nothing (use `sdd-reverse-engineer`), does not do security review (`sdd-security-auditor`), and does not edit `plan/`, `task/` or `test/`: those are regenerated by their owners through the normal cascade once the specs change.

Specs stay the source of truth (Art. 12). Reconcile documents what the code does and asks a human whenever the code might be wrong; a spec item that was never implemented is an implementation gap, never a reason to delete or deprecate the spec.

## 2. Invocation

| Mode | Behavior |
|------|----------|
| default | Classify, auto-resolve safe types after the summary, ask for the rest |
| `--dry-run` | Classify and report only; no spec changes |
| `--scope=<paths>` | Only compare the given code paths against their specs |
| `--code-wins` | The user declares the code authoritative (e.g. post-release sync): BEHAVIORAL_CHANGE and AMBIGUOUS items resolve toward code without prompts. BUG_OR_DEFECT items with failing tests and NOT_IMPLEMENTED items are still reported, not resolved |

## 3. Process

### Phase 1: Context Loading

1. Require `requirements/REQUIREMENTS.md` and `spec/`; if missing, stop: "No SDD artifacts found. Use `sdd-reverse-engineer` to generate them first."
2. Resolve code and test paths from the `## SDD Stack Profile` section of the root `CLAUDE.md` (`code_paths`, `test_paths`; see `sdd-task-implementer/references/stack-profile.md`), defaulting to `src/` and `tests/`. If no code exists there, stop: "No source code found. Nothing to reconcile."
3. Read `pipeline-state.json` and the previous `reconciliation/RECONCILIATION-REPORT.md` if present (for delta comparison).
4. Index the spec artifacts: REQ IDs with EARS statements, UCs, WFs, API operations (with the module's `Style`), entities, invariants, NFRs, BDD scenarios.

### Phase 2: Code Inventory

1. **Reuse gap detection when available.** If `.sdd/gap-analysis.json` (written by `sdd-gap-detector`) exists and its `generatedAt` is later than the last commit touching `spec/` or the code paths, seed the divergence list from it: `missing` → spec without code, `orphan` → code without spec, `mismatch` → behaviour differs. Only scan code for what it does not cover (business rules, state machines, entity fields). Otherwise, or if it is stale, fall back to scanning.
2. **Scan (fallback / complement).** Extract routes or operations with handlers, entities and fields, validations, state transitions, external integrations, config-driven behaviour, and the tests exercising them. Map code to spec via `Refs:` comments, commit trailers, endpoint paths, entity and naming conventions.
3. **Code intelligence (optional).** If the SDD MCP server is available, `sdd_context({ artifact_id })` gives the implementing code refs, tests and coverage of an artifact, which helps separate REFACTORING (same refs and passing tests, internals differ) from BEHAVIORAL_CHANGE.
4. **Test evidence.** Classification needs to know whether tests pass. Run the Stack Profile `test` command (or `test_file` for the relevant files) if the profile defines it; otherwise ask the user for the command or permission to skip. When tests were not run, record `Tests: not run` and do not use test results as evidence.

### Phase 3: Spec-Code Comparison

For each spec artifact, compare with its code counterpart: operation behaviour (inputs, outputs, errors; for `Style: http` modules also method, path, status codes), business rules and thresholds, state machines, entity fields and constraints. Produce three lists with evidence (spec `file:line`, code `file:line`, test status): spec without code, code without spec, both present but different. Before calling code "new", check it is not a renamed or moved feature.

### Phase 4: Classification

Read [references/divergence-classification.md](references/divergence-classification.md) and classify each divergence:

| Type | Signal | Resolution |
|------|--------|-----------|
| `NEW_FUNCTIONALITY` | Code without spec; tested or actively used | Auto: amend specs (CR ADD) |
| `REMOVED_FEATURE` | Spec without code; git history shows the code was deliberately removed | Auto: deprecate in specs (CR DEPRECATE) |
| `NOT_IMPLEMENTED` | Spec without code; no history of an implementation | Never auto-resolved: reported as an implementation gap |
| `BEHAVIORAL_CHANGE` | Both exist, behaviour differs, tests agree with code | Ask the user |
| `REFACTORING` | Structure changed, behaviour equivalent | Auto: update technical references in specs |
| `BUG_OR_DEFECT` | Code contradicts spec and tests fail or are missing | Ask the user |
| `AMBIGUOUS` | Evidence insufficient or contradictory | Ask the user |

Confidence (HIGH / MEDIUM / LOW) follows the evidence rules in that reference; LOW always becomes `AMBIGUOUS`.

### Phase 5: Reconciliation Plan

Read [references/reconciliation-strategies.md](references/reconciliation-strategies.md). Draft every spec amendment as a change-request entry in the format of `sdd-req-change/references/change-request-template.md` (`CR-NNN`, Type ADD / MODIFY / DEPRECATE, affected REQs, draft EARS statement), with the divergence evidence as its Motivation. Collect them in `changes/CR-RECONCILE-{YYYY-MM-DD}.md`. For user-decision types, prepare the question with spec excerpt, code behaviour and test status. Compute which pipeline stages become stale (Phase 8 rules).

### Phase 6: User Review

Always show the summary before applying anything, including auto-resolvable items:

```
Reconciliation Summary
Auto-resolve:  NEW_FUNCTIONALITY {n} · REMOVED_FEATURE {n} · REFACTORING {n}
Gaps reported: NOT_IMPLEMENTED {n}
Your decision: BEHAVIORAL_CHANGE {n} · BUG_OR_DEFECT {n} · AMBIGUOUS {n}
Pipeline impact: stages {…} will become stale
```

MEDIUM-confidence auto items are listed individually so the user can veto them. For each decision item:

```
DIVERGENCE #{N}: {title}
  Spec says: {EARS statement or spec excerpt}
  Code does: {observed behaviour}
  Tests: {pass | fail | missing | not run}

  (A) Code is correct → amend spec to match code (CR MODIFY)
  (B) Spec is correct → record a defect; code must change
  (C) Both need changes → hand the CR to sdd-req-change
  (D) Defer → leave the divergence documented
```

This A-D mapping is the same for every decision type. For AMBIGUOUS items, first ask which type applies, then offer A-D. `--dry-run` shows the summary and stops; `--code-wins` answers (A) for BEHAVIORAL_CHANGE and AMBIGUOUS.

### Phase 7: Apply Changes

Write only to `requirements/`, `spec/` (canonical tree of `sdd-specifications-engineer`, § "Specification Folder Structure"), `changes/` and `reconciliation/`:

- **NEW_FUNCTIONALITY / option A:** apply the CR: requirement in `requirements/REQUIREMENTS.md` with the next free `REQ-F-NNN` / `REQ-NF-NNN`; use case in `spec/use-cases/UC-NNN-{slug}.md` and scenarios in `spec/tests/BDD-UC-NNN.md`; operations in `spec/contracts/API-{module}.md` (keeping the module's `Style`); entities in `spec/domain/02-ENTITIES.md`, rules in `spec/domain/05-INVARIANTS.md`, NFRs in `spec/nfr/*.md`; add the REQ row to `spec/TRACEABILITY-MATRIX.md`. Add an ADR in `spec/adr/` only if the change is architecturally significant.
- **REMOVED_FEATURE:** mark the REQ and the artifacts that serve only it `[DEPRECATED]` with date and reason; never delete.
- **REFACTORING:** update code references (paths, symbol names, `Style: http` paths) inside spec documents only. References in `plan/`, `task/` or `test/` are listed in the report for their owners to regenerate.
- **Option B (defect) and NOT_IMPLEMENTED:** no spec change. Record the item in the report and recommend `/sdd-task-generator --fase=N --incremental` for the FASE that owns the requirement (or `/sdd-gap-detector` for a full gap view).
- **Option C:** leave the CR in `changes/` and recommend `/sdd-req-change --file changes/CR-RECONCILE-{date}.md`.

Each divergence is applied independently; a failure in one does not block the others. Mark added or changed items `[RECONCILED]` / `[UPDATED]` with the CR ID. Before the first commit, work on a branch when on the default one: `node "${SDD_PLUGIN_ROOT:-$CLAUDE_PLUGIN_ROOT}/scripts/sdd.mjs" branch start change CR-RECONCILE-{date} reconcile` (branch rule in the plugin-root `references/git-conventions.md`). Commit the spec changes with `git commit -m "docs(specs): reconcile spec-code drift" --trailer "Change: {CR IDs}" --trailer "Refs: {affected REQ/UC IDs}"`; when the harness asks for an attribution line, add it with `--trailer` too. Ask before merging the branch (merge commit or PR) or pushing.

### Phase 8: Pipeline State and Report

1. Mark stages stale per the canonical rules (CLAUDE.md, `sdd-req-change/references/cascade-patterns.md`): a change in `requirements/` makes `specifications-engineer` and everything after it stale; a change in `spec/` makes `spec-auditor` and everything after it stale. Reconcile never writes `plan/` or `task/`, so it never originates a staleness from there. Record `staleReason: "reconcile {date}"`.
2. Read [references/reconciliation-report-template.md](references/reconciliation-report-template.md) and write `reconciliation/RECONCILIATION-REPORT.md`.
3. Commit the report and the CR file: `git add reconciliation/ changes/CR-RECONCILE-{date}.md`, then `docs(changes): reconciliation report {date}` with `Refs:` the affected REQ ids, skipped when nothing is staged (plugin-root `references/git-conventions.md` § Stage outputs are committed).
4. Do not invoke downstream skills; list the recommended next commands (normally `/sdd-spec-auditor`, then `/sdd-acceptance --check`).

## 4. Pipeline Integration

**Reads:** `requirements/REQUIREMENTS.md`, `spec/`, code and test paths (read-only), `.sdd/gap-analysis.json` (optional), `pipeline-state.json`, previous report.
**Writes:** `requirements/REQUIREMENTS.md`, `spec/` documents, `changes/CR-RECONCILE-{date}.md`, `reconciliation/RECONCILIATION-REPORT.md`, `pipeline-state.json` (stale markers).

| Skill | Relationship |
|-------|-------------|
| `sdd-pipeline-status --diagnose` | Recommends reconcile for SDD drift |
| `sdd-reverse-engineer` | Use instead when no SDD artifacts exist |
| `sdd-gap-detector` | Its `.sdd/gap-analysis.json` seeds Phases 2-3 |
| `sdd-req-change` | Owns the CR format; option C hands CRs to it |
| `sdd-spec-auditor` | Run next to audit the amended specs |
| `sdd-task-generator` | `--fase=N --incremental` turns defects and gaps into tasks |
| `sdd-acceptance` | `--check` verifies chain integrity and the verdict per requirement afterwards |

Every classification cites spec location, code location and test status. Output language follows the user's language; technical terms stay in English.
