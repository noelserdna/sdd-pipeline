# SDD Verify Coverage (P3 — LLM-as-Judge Heuristic Layer)

**Version**: 1.0.0
**SWEBOK**: Ch08 (Software Testing — coverage analysis), Ch09 (Software Quality — verification)
**Purpose**: Catch-all heuristic layer that verifies requirement coverage by asking structured binary questions about whether source code implements specified requirements. Produces confidence-scored verification results written to `.sdd/verification-results.json`.

## Trigger Phrases

- `/sdd-verify-coverage`
- "verify coverage"
- "check implementation"
- "are requirements implemented"
- "verificar cobertura"
- "LLM verification"

## Prerequisites

- Source code in `src/` (or project source root)
- Existing SDD artifacts: at least `requirements/` and `spec/`
- `dashboard/traceability-graph.json` generated by `/sdd-dashboard`
- **Optional**: `.sdd/gap-analysis.json` from `/sdd-gap-detector` (enriches candidate selection)

## Process

### Phase 1 — Identify Uncovered Requirements

1.1. Read `dashboard/traceability-graph.json`
  - IF missing: suggest running `/sdd-dashboard` first -> STOP

1.2. Scan all artifacts of type `REQ` in the graph. For each REQ, classify coverage status:

| Status | Condition |
|--------|-----------|
| **covered** | Has `codeRefs[]` with at least one entry where `origin` is `"linked"` or `"commit-inferred"` AND confidence >= 0.8 |
| **weakly-covered** | Has `codeRefs[]` but all entries have `origin = "task-inferred"` (lowest confidence tier) |
| **uncovered** | Has empty `codeRefs[]` or no `codeRefs` field at all |

1.3. Also read `.sdd/gap-analysis.json` if it exists:
  - Extract `missingEndpoints`, `orphanRoutes`, `schemaMismatches`, `uncoveredBDD` for additional context
  - Cross-reference with uncovered REQs to prioritize verification targets

1.4. Build the **verification target list**: all REQs classified as `uncovered` or `weakly-covered`, sorted by priority:
  1. REQs linked to uncovered BDD scenarios (from gap analysis)
  2. REQs with no codeRefs at all
  3. REQs with only task-inferred codeRefs

1.5. For each target REQ, collect:
  - REQ ID and title (from the artifact node)
  - Linked UC IDs (via `relationships[]`)
  - Linked BDD scenario IDs (via `relationships[]`)
  - Domain classification (from `domain` field if present)

1.6. Print summary to user:
```
Phase 1 complete.
- Total REQs in graph: X
- Already covered (skipped): Y
- Weakly covered (will verify): Z
- Uncovered (will verify): W
- Total verification targets: Z + W
```

### Phase 2 — Find Candidate Files

For each verification target REQ:

2.1. **Task-based search**: Follow the REQ's relationship chain:
  - REQ -> UC -> WF -> TASK (via `relationships[]` in the graph)
  - For each linked TASK, check if the task document references specific `src/` files
  - Read the task document (e.g., `task/TASK-FASE-*.md`) and extract file paths mentioned

2.2. **Domain-based search**: Use the REQ's domain classification:
  - If REQ has `domain: "auth"`, search `src/**/auth/**`, `src/**/*auth*`
  - If REQ has `domain: "payment"`, search `src/**/payment/**`, `src/**/*pay*`
  - Extract keywords from the domain name and search matching directory structures

2.3. **Keyword search**: Extract significant keywords from the REQ title:
  - Strip common words (the, shall, must, when, system, a, an, is, are, be, will, should)
  - Use remaining keywords to Grep across `src/` files
  - Limit to top 10 file matches by keyword density

2.4. **Deduplicate and rank** candidate files per REQ:
  - Files found via task references: priority 1
  - Files found via domain match: priority 2
  - Files found via keyword match: priority 3
  - **Cap at 5 candidate files per REQ** to limit verification scope

2.5. **Skip already-linked files**: If a candidate file is already linked to this REQ with confidence >= 0.8 in the traceability graph, skip it.

2.6. Print progress:
```
Phase 2 complete.
- Verification pairs generated: N
- Average candidates per REQ: M
- REQs with 0 candidates (no code found): K
```

### Phase 3 — Structured Verification

For each (REQ, candidate_file) pair:

3.1. Read the requirement text:
  - From `requirements/REQUIREMENTS.md`, find the full requirement statement for the REQ ID
  - Include any EARS syntax elements (WHEN/THE/SHALL)

3.2. Read the candidate file:
  - Read the first 200 lines of the file
  - If the file is shorter than 200 lines, read the entire file

3.3. Perform the **structured verification check** by self-prompting with the following template (from `references/verification-prompt.md`):

```
VERIFICATION CHECK
==================
Requirement: {REQ-ID}: "{requirement_text}"
File: {file_path}
File content (first 200 lines):
---
{content}
---

Does this file contain code that directly implements the above requirement?

Answer in EXACTLY this JSON format:
{
  "implements": true|false,
  "evidence": "Brief quote or description of the implementing code (or 'No matching implementation found')",
  "confidence": 0.0-1.0
}

Confidence scoring guide:
- 0.9-1.0: Clear, direct implementation (matching function names, signatures, logic)
- 0.7-0.8: Indirect implementation (helper functions, partial coverage, shared utilities)
- 0.5-0.6: Possible but ambiguous (generic code that could relate)
- Below 0.5: Unlikely match
```

3.4. Parse the structured response:
  - Extract `implements`, `evidence`, and `confidence` fields
  - Validate that `confidence` is a number between 0.0 and 1.0

3.5. Apply acceptance threshold:
  - **Accept** results where `implements == true` AND `confidence >= 0.7`
  - **Mark as uncertain** results where `implements == true` AND `confidence` is 0.5-0.69
  - **Reject** results where `implements == false` OR `confidence < 0.5`

3.6. For accepted results, generate a `suggestedRef`:
  - Format: `// Refs: {REQ-ID}` (the comment that could be added to the source file)
  - This is a SUGGESTION only; this skill never modifies source files

3.7. Print running progress every 10 checks:
```
Verified: X/Y pairs | Found: A implementations | Uncertain: B | Not found: C
```

## Constraints

- **C-01**: Read-only on `src/` and `spec/` — only writes to `.sdd/verification-results.json`
- **C-02**: Uses structured prompts with binary answers (not quality judgments)
- **C-03**: Maximum 5 candidate files per REQ to limit scope and cost
- **C-04**: Skip files already linked with confidence >= 0.8 in the traceability graph
- **C-05**: Results are suggestions, not ground truth — origin = "llm-verified" has variable confidence
- **C-06**: Does NOT modify any existing traceability artifacts (graph, gap analysis, etc.)
- **C-07**: Does NOT modify source code files (no auto-injection of Refs: comments)
- **C-08**: If `dashboard/traceability-graph.json` does not exist, direct user to `/sdd-dashboard` -> STOP
- **C-09**: Tolerate partial pipelines — if `requirements/` or `spec/` are missing, report and STOP
- **C-10**: All confidence scores must be between 0.0 and 1.0 inclusive
